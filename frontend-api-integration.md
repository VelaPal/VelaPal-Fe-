# VelaPal V6.1.1 frontend integration report

The frozen `velapal-v6.1-api-contract.md` is the source of truth and was not modified. No Express, FastAPI, provider service or internal endpoint was changed or called by the frontend.

## Audit and implementation

The existing App Router frontend uses feature components, contract services and workspace-scoped SWR. The audit found an embedded Next API mock, an upload mock route, a shared synthetic operation ID on the dashboard, demo credentials/OTP hints, tab-persisted registration/recovery and Customer/Seller/Admin preview stores. Several services already matched the frozen routes but assumed additional mock metadata, fuller Admin detail fields or a hardcoded API origin.

The runtime mock routes and mock startup script have been removed. All fixtures, simulator adapters and synthetic preview reducers now live under `tests/fixtures/`. Existing preview hooks return empty, disabled view state and cannot mutate or read tab storage. Existing unavailable branches preserve the relevant routes and visual components. Seller catalog cards and Admin transaction monitoring now bind authorized API records; unsupported editing remains disabled. Public account forms no longer simulate verification, reset or signup. No CSS, design token, navigation destination or dependency was changed.

`lib/api.ts` owns native fetch, environment-derived public prefix, cookie credentials, in-memory CSRF, quoted If-Match, idempotency headers, cancellation, bounded timeouts, envelope validation and structured errors. A compatibility export retains old import paths. All services validate DTOs before reporting success. File upload is the only byte transfer, using a backend-issued storage URL with credentials omitted. No retries of mutations occur automatically.

Session recovery applies CSRF only after the response is current. Workspace transitions abort requests, remount scoped caches and hide protected data during switching. An uncertain workspace-switch outcome requires session recovery. Proposal acknowledgment is bound to the exact terms/version/hash/expiry and is invalidated when those change. Settlement requires the current server capability, all three distinct required consents, current proposal, running control and no pending/unknown operation. An accepted operation ID is tracked immediately without claiming a verified refund.

## Integration blockers and schema limits

1. Checkout: ?3.8 names routes but does not define a create request, buyer approval response or capture handoff. Existing dialog stays available for quote review; payment submission is disabled.
2. Consent bindings: source sharing and mediation require authoritative `paramsHash`; proposal creation requires a current `sourceDigest`. The public contract does not define how to obtain these. The former mock extensions are removed. No client hash is generated. Existing returned proposal terms can still receive exact consent and authorized execution.
3. Unsupported endpoints: signup, email verification/resend, password recovery/reset, preferences/profile editing, subscriptions/reminders, digital entitlements/downloads, notifications, merchant applications/review, fulfillment/tracking, product add/edit/publish/archive, user suspension, invitations, other-session revocation, staff grants, global AI administration and operational telemetry/reporting have no public definitions. Existing routes show unavailable/disabled states. The Seller business assistant links to actual case preparation; its old scripted summary is disabled.
4. Incomplete DTO definitions: catalog, workspace list, transaction list, dispute list and private run results lack complete frozen JSON schemas. Existing minimal `{items}`/catalog view shapes are retained and validated, with no invented route or fallback. Shape mismatches show `INVALID_RESPONSE`. Unknown filter/pagination requests are not invented. Authorized preview URLs are used only if returned; their field naming needs BE confirmation.
5. Pre-auth CSRF: ?1.1 requires session-bound CSRF on all browser mutations, but login/session-login MFA examples provide no pre-auth CSRF bootstrap. Authenticated mutations always require the token. Initial login and login MFA can proceed without it, using the documented authentication payload and browser-managed Origin; they include CSRF when available. Confirm Express's pre-auth Origin/CSRF policy before deployment; no undocumented bootstrap endpoint was added.
6. Live environment: Express `http://localhost:4000/api/v1/auth/session` could not be reached. CORS/preflight, secure cookie deployment, grants, storage/scan ACLs, AI quality, refunds, provider reconciliation and durable workflow execution need live acceptance testing. No real E2E success is claimed.
